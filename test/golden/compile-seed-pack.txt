## Scout standing instructions

- For large features — multi-file, multi-day, or architecturally novel — plan first, then build with an agent team: a dedicated orchestrator, a reviewer, and several build subagents. Assign models per task — capable models for orchestration and review, lighter models for well-specified builds — keeping cost and tokens reasonable.
- When a project begins, create CHANGELOG.md at the repo root. Then maintain it for the life of the project: whenever a meaningful, user-visible change lands, append a dated entry describing it in one or two plain-language lines — as part of landing the change itself, never batched for later. Keep the newest entries at the top.
- Maintain DECISIONS.md as an append-only log of meaningful project decisions. One entry per decision, newest last: a short numbered title (D-001, D-002, …), the date, a status (proposed → accepted), and the reasoning in a few sentences. An overturned decision is never deleted — it stays in the log marked superseded by its successor. Record each decision at the moment it is made, while the reasoning is fresh; create the file on the first decision if it does not exist yet.
- After any stakeholder demo, or when a major feature first works end-to-end, prompt to capture screenshots of the working state. Save them inside the project with the date and a short label, so the build keeps a visual history of what worked when. Prompt, then capture — never screenshot silently.
